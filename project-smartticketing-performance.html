공통 환경

Java 21 · MySQL 8.4 · Redis 7 · k6 컨테이너. 모든 회차는 120석 기준이며, 제공된 기록상 전후 동일 데이터·부하·자원 조건으로 비교했습니다.

SQL 실행 횟수와 결과 행은 HTTP 요청 스레드의 JDBC 계측값입니다. 별도 워커의 SQL, DB 내부 스캔 행 수, 네트워크 전송 바이트는 포함하지 않습니다.

대기 순번 조회

순번 계산 SQL: 개선 전 8회 / 8요청, 개선 후 0회 / 8요청. JDBC 결과 행: 개선 전 1,028행 / 8요청, 개선 후 24행 / 8요청. 여기서 순번 계산 SQL은 waiting_queues의 COALESCE 순번 비교 쿼리를 뜻하며, 다른 DB 접근이 모두 사라졌다는 뜻은 아닙니다.

좌석도 조회

개선 전 122회 / 61요청, 개선 후 6회 / 60요청입니다. 캐시 적중·미스를 포함한 JDBC 실행 횟수이며 이 수치만으로 정확한 캐시 적중률을 역산하지 않습니다.

상영시간표 조회

좌석 재고 결과 행은 개선 전 146,400행 / 61요청, 개선 후 7,200행 / 61요청입니다. 행 수 감소는 반복 재고 조회를 생략한 효과를 보여주며, 필드 축소에 따른 바이트·메모리 절감은 별도 측정하지 않았습니다.

자동 선점 흐름

순번 확인 → 취소 → HOLDING → 대상 좌석 확인까지 모두 성공해야 성공 1건으로 계산했습니다. 개선 전 1/4건, 개선 후 4/4건입니다. 데드락 수는 로그의 Hibernate WARN 줄 수이며 잠금 순환 개수 자체는 아닙니다. 잠금 그래프가 없어 정확한 행·인덱스 간 잠금 순환은 확인되지 않았습니다.

주의 사항

Redis 캐시뿐 아니라 DB 조회·잠금·Outbox 변경을 포함한 종합 비교입니다. 결과는 제한된 스모크 테스트에서 관찰한 값이며, 운영 성능이나 장애 복구·exactly-once 보장을 의미하지 않습니다.

03NEXT LOAD TEST PLAN

다음 측정은 단계별 부하와 지연 분포로

현재 결과는 쿼리 비용과 소규모 동시성 흐름에 집중되어 있습니다. 응답 시간이나 처리 한계는 아직 측정 완료로 표현하지 않습니다.

01 / RAMP-UP계획

가상 사용자 단계 증가

테스트 데이터와 실행 환경을 고정하고 1 → 5 → 10 → 20 VU 순으로 부하를 높입니다. 각 단계는 램프업 이후 동일한 유지 시간으로 반복해 조건 차이를 줄입니다.

02 / LATENCY & THROUGHPUT미측정

응답 시간 분포와 처리량

HTTP p50·p95·p99, RPS, 오류율, DB connection pool 대기, CPU·메모리를 기록합니다. k6의 요청 처리량과 JDBC 행 수를 같은 지표로 혼용하지 않습니다.

03 / BREAKING POINT미측정

한계 구간 식별

지연과 오류가 급증하거나 정합성 검증이 실패하는 부하 단계를 한계 후보로 기록합니다. EC2는 메모리·Swap 한도를 고려해 로컬에서 먼저 탐색하고, 운영 환경은 낮은 단계부터 확인합니다.

04 / CORRECTNESS필수 검증

성능과 정합성을 함께 평가

동시 선점 중 중복 활성 예약, 대기 순번 불일치, 취소 후 자동 배정 누락을 검사합니다. 평균 응답 시간만 낮아지고 정합성이 깨지는 결과는 개선으로 판정하지 않습니다.

판정 원칙: 현재 포트폴리오에는 p50·p95·p99, RPS/TPS, breaking point의 실측값이 없습니다. 위 내용은 다음 검증 계획이며 완료된 테스트 결과가 아닙니다.
03 / CONCLUSION

수치의 의미와 한계까지 함께 기록

이번 결과는 대기 순번 계산 SQL, 반복 조회에서 발생한 SQL과 JDBC 결과 행, 취소 후 자동 선점 흐름의 성공 여부를 비교한 것입니다. 제한된 테스트에서 관찰한 변화이며, 실제 운영 트래픽의 응답 시간이나 처리량 개선율로 해석하지 않았습니다. 다음 검증 단계에서는 충분한 반복 횟수와 동시 사용자 규모를 확보하고 p50·p95 응답 시간, 오류율, 처리량, 자원 사용량을 함께 측정해야 합니다.
