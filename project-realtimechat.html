02TECHNICAL TRADE-OFFS

빠른 전달과 정합성 사이의 선택

선택한 기술이 해결하는 문제뿐 아니라 보장하지 못하는 조건도 함께 기록했습니다.

SESSION vs JWT

브라우저 세션을 선택한 이유와 비용

현재 서비스는 브라우저 중심의 웹 채팅이므로 서버에서 세션을 무효화할 수 있는 HTTP Session을 사용합니다. JWT를 쓰면 요청별 서버 세션 조회 의존성을 줄일 수 있지만, 로그아웃·권한 변경 직후 토큰을 무효화하는 별도 전략이 필요합니다. 반대로 세션 방식은 앱 인스턴스 간 세션 공유가 필요해 Nginx ip_hash로 라우팅을 고정했으며, 이는 장애 전환 시 세션 공유를 해결하지는 않습니다.

MYSQL vs REDIS

영속 데이터와 실시간 이벤트를 분리

사용자·채팅방·메시지와 읽음 위치는 MySQL에 저장해 영속성과 조회 근거를 유지합니다. Redis Pub/Sub은 인스턴스 간 이벤트 전달에 사용합니다. Redis를 메시지 원장으로 사용하지 않아 DB와 이벤트 브로커의 책임을 구분했지만, Pub/Sub은 내구성 있는 큐가 아니므로 구독자가 놓친 이벤트의 재생이나 엄격한 순서를 보장하지 않습니다.

PUB/SUB vs DURABLE QUEUE

낮은 복잡도 대신 전달 보장 범위를 제한

Redis Pub/Sub은 기존 Redis를 활용해 구현이 단순하고 실시간 중계에 적합합니다. Kafka 같은 내구성 있는 로그를 도입하면 재생·소비 위치 관리의 선택지가 늘지만 운영 자원과 구성 복잡도가 커집니다. 현재 EC2 자원 제약을 고려해 Pub/Sub을 유지하되, 메시지 순서 보장은 미해결 과제로 명시합니다.

AI / CODE REVIEW

제안보다 재현 가능한 검증 결과를 우선

AI가 제안한 코드와 아키텍처도 그대로 병합하지 않고 인증 우회 가능성, 쿼리·트랜잭션 실행 경로, 동시성 경계, 장애 시 fallback, 메모리 비용을 기준으로 검토합니다. 변경 후에는 동일 조건의 기능·부하 테스트로 판단합니다. 실제 사례로 Redis listener를 단일 스레드로 직렬화한 실험은 성능 회귀가 확인돼 되돌렸습니다. 메시지 순서 문제도 해결됐다고 포장하지 않고, 테스트에서 관측된 역전과 sequence gap을 남겼습니다.

검증 범위와 미측정 지표

현재 기록에는 전달 평균·p95·최대값이 있지만 p50·p99, RPS/TPS, 오류율이 급증하는 breaking point를 동일한 반복 조건에서 확정한 결과는 없습니다. 다음 테스트에서는 로컬에서 1→5→10→20 VU로 단계적으로 올리고 각 단계에서 동일 데이터·메시지 간격·실행 시간을 유지한 반복 테스트를 수행한 뒤, EC2는 자원 한도를 고려해 더 낮은 단계부터 검증해야 합니다. HTTP p50/p95/p99·RPS·요청 실패율·WebSocket 연결 실패·교차 인스턴스 전달 지연·CPU/RAM/Swap을 함께 기록하고, 오류율이나 지연이 급격히 증가하는 지점을 breaking point 후보로 기록합니다.

OBSERVABILITY

Prometheus + Grafana

Actuator/Micrometer 메트릭을 수집해 HTTP 지연과 JVM 및 프로세스 상태를 관찰할 수 있도록 구성했습니다. 운영 자원 사용량 때문에 필요 시 프로필로 켜는 방식입니다.

측정 해석

이전 5 VU 저부하 실행에서는 HTTP 요청 실패 0%, WebSocket 연결 23/23, 교차 인스턴스 전달 360건·p95 27ms가 기록됐습니다. 이후 2 VU / 60초 / 100ms 간격 테스트는 전달 1,158건·평균 18.96ms·p95 34ms였습니다. 조건이 서로 다르므로 두 결과를 직접적인 개선율로 비교하면 안 됩니다.

04DEPLOYMENT & DEVELOPMENT

로컬 개발과 EC2 배포 흐름

개발 환경과 운영 환경을 분리하고, GitHub Actions에서 테스트·배포 작업을 관리합니다.

LOCAL

PowerShell + Docker Compose

start-local.ps1과 stop-local.ps1로 로컬 실행 환경을 관리합니다. 로컬 전용 MySQL·Redis 포트를 운영 포트와 분리해 개발 PC의 기존 서비스와 충돌을 줄입니다.

CI

Pull Request 검증

.github/workflows/ci.yml은 JDK 21, MySQL, Redis 환경에서 Gradle 테스트를 실행합니다.

EC2 CD

main push 기반 배포

deploy-ec2.yml은 main 푸시 시 self-hosted Windows runner에서 SSH로 EC2에 접속해 저장소를 갱신하고 Compose 서비스를 재배포하도록 구성돼 있습니다. 배포 성공 후에도 실제 로그인과 채팅 동작을 별도로 확인해야 합니다.

MONITORING

필요할 때만 실행

운영 기본 구성은 Nginx, 두 앱 인스턴스, MySQL, Redis 중심입니다. Prometheus와 Grafana는 --profile monitoring으로 별도 실행합니다.

OPEN ISSUE

동시 메시지의 방 단위 순서 보장

강한 테스트에서 메시지 순서 역전 6건과 도착 시점 sequence gap 6건이 관측됐습니다. gap은 늦게 도착한 메시지 때문에 생길 수 있어 실제 유실과 구분하는 검증 로직도 추가 확인이 필요합니다.

Redis listener를 단일 스레드로 직렬화한 시도는 성능 회귀가 커서 되돌렸습니다. 현재는 순서 보장이 완료된 것으로 표시하지 않고, DB 저장부터 Redis 발행·수신과 STOMP 전달까지 단계를 나눠 추적하는 것을 다음 과제로 두고 있습니다.
